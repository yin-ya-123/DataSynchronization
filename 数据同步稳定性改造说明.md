# 数据同步接口 —— 稳定性改造调整说明

> 版本：v1.0　　日期：2026-11-03　　适用范围：`Template`（后端 Spring Boot 2.7.12）
> 本文为**调整说明**，本次仅输出文档，未修改任何业务代码。

---

## 0. 改造目标与范围

| 目标 | 现状 | 改造后 |
|---|---|---|
| G1 第三方库不可用时，服务不假死、不需要重启 | 失败一次后持续报错，线程池耗尽，必须重启 | 熔断 + 快速失败，服务持续可用 |
| G2 慢查询（1~5 分钟）不被误杀 | 无查询级超时保护，慢查询可能永久占用连接 | Oracle 读超时 10 分钟 + 建连超时 5 秒 |
| G3 单个任务/单条明细失败不影响其它任务 | 明细级无 try/catch，一条失败整条任务终止 | 三层 try/catch 隔离 |
| G4 批量写入且能定位到具体失败行 | 逐行 INSERT，失败只记一条汇总错误 | 分块批量 + 精确到行的失败定位 |
| G5 失败记录本地可查，不依赖数据库 | 失败信息写 `error_log` 表，库挂了就没了 | 独立本地文件日志 + 行级明细 |
| G6 cron 重试不产生大面积重复插入风险 | 全量重跑，重复插入 → 主键冲突 | 本次按约定**不做幂等改造**，仅在文档中标注风险 |

### 支持的数据库类型

系统为**多数据源**架构，`sys_datasource.ds_lx` 支持三种（见 `DBFieldInfoService.java:18`）：

| ds_lx | 数据库 | 驱动 | 本次方案中需区分的方言点 |
|---|---|---|---|
| `ORACLE` | Oracle | `ojdbc8 21.1.0.0` | 超时属性名/单位、日期占位符 `to_date()`、批量失败语义 |
| `SQLSERVER` | SQL Server | mssql-jdbc | 超时属性名/**单位为秒**、URL 用 **`;`** 分隔、批量失败**无 -3 标记** |
| `MYSQL` | MySQL | mysql-connector-j | 超时属性名/单位、URL 用 `?` 分隔、可开 `rewriteBatchedStatements` |

> **源库与目标库可以不同**（如 Oracle 查询 → SQL Server 插入），本文所有改造均按"**源/目标各自独立**"设计。
> 方言相关的差异集中在 **§5 多数据源方言适配**，改造时务必对照。

### 数据源实体的三个新字段（2026-11-03 新增）

`SysDatasource` 实体（`Template/src/main/java/com/yin/pojo/dataflowdb/SysDatasource.java:22-24`）新增：

```java
    private String ip;                 // 数据库服务器 IP
    private String schemaName;         // 模式名（Oracle schema / SQL Server schema / MySQL database）
    private String connectionParams;   // 附加连接参数（如超时参数）
```

这三个字段正好对应本次改造的三个痛点，是本次改造的**数据基础**：

| 字段 | 解决的问题 | 对应章节 |
|---|---|---|
| `connectionParams` | 超时参数不再塞 URL，改由独立字段维护；不同库的分隔符差异由代码统一处理 | §5.1 §5.2 §6 |
| `schemaName` | 修复「SQL Server / MySQL 取字段信息不按 schema 过滤」的既有 bug；目标表名可自动补 schema | §5.7 |
| `ip` | 熔断/探活失败时能直接定位到"哪台机器"，排查第三方库问题必备 | §5.7 |

> ⚠️ **数据库表需要同步加列**（MyBatis-Plus 驼峰映射已开启，列名必须用下划线形式）：
> `ip` / `schema_name` / `connection_params`。DDL 见 §6。

### 明确不在本次范围内（已确认）

- **不做 MERGE / 幂等写入改造**。按约定"不用管对方库的插入情况，只是根据自己设置的 cron 重试"。
  ⚠️ 遗留风险：cron 重跑会对上一轮已成功的行重复 INSERT。若目标表有唯一约束，重跑会触发 `ORA-00001`，
  这些行会被记入本地失败日志（属预期行为，不影响其它行）。详见 §9。

## 1. 现状问题定位（含证据）

| # | 问题 | 证据位置 | 后果 |
|---|---|---|---|
| P1 | Hikari 取连接超时 60s，失败极慢 | `SysDatasourceServiceImpl.java:140` `setConnectionTimeout(60000)` | 每次失败干等 1 分钟，线程被占满 |

| P20 | 连接参数只能塞在 URL 里 | `sys_datasource.url` 单字段 | 每加一个超时参数就要改一次 URL；三种库分隔符还不一样（`?` / `;`），极易写错且难排查 |
| P21 | 数据源只有 URL，没有 IP 信息 | `sys_datasource` 表结构 | 熔断/探活失败时无法定位到"哪台机器"，第三方库多实例时排查困难 |

## 3. 新增文件

### N1 `Template/src/main/java/com/yin/utils/dataBase/DataSourceCircuitBreaker.java`

**作用**：按 `dsKey` 维度的熔断器。只有"连接类"异常才计入熔断；数据类异常（SQL 语法、约束冲突）不熔断，直接定位到行。

**完整代码**：

```java
package com.yin.utils.dataBase;

import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;

import java.net.ConnectException;
import java.net.SocketTimeoutException;
import java.sql.SQLNonTransientConnectionException;
import java.sql.SQLRecoverableException;
import java.sql.SQLTimeoutException;
import java.sql.SQLTransientConnectionException;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * 数据源熔断器（按 dsKey 维度）
 *
 * 触发条件：连续 FAIL_THRESHOLD 次"连接类"异常 -> 打开熔断 OPEN_MILLIS 毫秒
 * 熔断期间：对该数据源的所有操作直接跳过（秒级返回），不再发起建连、不再刷 ERROR 堆栈
 * 半开：熔断期结束后放行一次，成功则完全恢复，失败则重新计时
 */
@Slf4j
@Component
public class DataSourceCircuitBreaker {

    /** 连续失败多少次后打开熔断 */
    private static final int FAIL_THRESHOLD = 3;
    /** 熔断持续时间（毫秒） */
    private static final long OPEN_MILLIS = 60_000L;

    private final ConcurrentHashMap<String, State> states = new ConcurrentHashMap<>();

    private static class State {
        final AtomicInteger fails = new AtomicInteger();
        volatile long openUntil = 0L;
    }

    /**
     * 熔断是否处于打开状态。打开时调用方应直接跳过本轮任务。
     */
    public boolean isOpen(String dsKey) {
        State s = states.get(dsKey);
        if (s == null) {
            return false;
        }
        long now = System.currentTimeMillis();
        if (now < s.openUntil) {
            return true;
        }
        if (s.fails.get() > 0) {
            // 半开：放一个请求试水
            s.openUntil = 0L;
            s.fails.set(0);
            log.info("数据源 {} 熔断期结束，进入半开状态", dsKey);
        }
        return false;
    }

    /**
     * 记录一次失败。仅连接类异常计入熔断。
     *
     * @param dsKey 数据源标识
     * @param ip    数据库服务器 IP（可为 null，仅用于日志定位到具体机器）
     * @param t     异常
     */
    public void onFailure(String dsKey, String ip, Throwable t) {
        if (!isConnectionError(t)) {
            return;
        }
        State s = states.computeIfAbsent(dsKey, k -> new State());
        int n = s.fails.incrementAndGet();
        log.warn("数据源 {} (ip={}) 连接失败(连续第 {} 次): {}", dsKey, ip, n, rootMessage(t));
        if (n >= FAIL_THRESHOLD && System.currentTimeMillis() >= s.openUntil) {
            s.openUntil = System.currentTimeMillis() + OPEN_MILLIS;
            log.error("数据源 {} (ip={}) 连续失败 {} 次，熔断 {} 秒，期间相关任务将快速跳过",
                    dsKey, ip, n, OPEN_MILLIS / 1000);
        }
    }

    /** 兼容调用：不含 ip */
    public void onFailure(String dsKey, Throwable t) {
        onFailure(dsKey, null, t);
    }

    /**
     * 记录一次成功，重置熔断计数。
     */
    public void onSuccess(String dsKey) {
        State s = states.get(dsKey);
        if (s != null && s.fails.get() > 0) {
            s.fails.set(0);
            s.openUntil = 0L;
            log.info("数据源 {} 恢复成功，熔断计数已重置", dsKey);
        }
    }

    /**
     * 判断是否为"连接类"异常（可重试 / 可熔断）。
     * 数据类异常（SQL 语法错误、唯一约束冲突、字段超长）返回 false。
     */
    public static boolean isConnectionError(Throwable t) {
        for (Throwable c = t; c != null; c = c.getCause()) {
            if (c instanceof SQLTimeoutException) {
                // 查询超时属于负载/数据问题，不熔断
                return false;
            }
            if (c instanceof org.springframework.jdbc.CannotGetJdbcConnectionException) {
                return true;
            }
            if (c instanceof SQLTransientConnectionException
                    || c instanceof SQLRecoverableException
                    || c instanceof SQLNonTransientConnectionException
                    || c instanceof ConnectException
                    || c instanceof SocketTimeoutException) {
                return true;
            }
            if (c.getCause() == c) {
                break;
            }
        }
        return false;
    }

    /**
     * 取最底层异常信息，便于日志定位。
     */
    public static String rootMessage(Throwable t) {
        Throwable c = t;
        while (c.getCause() != null && c.getCause() != c) {
            c = c.getCause();
        }
        String msg = c.getMessage();
        return c.getClass().getSimpleName() + (msg == null ? "" : ": " + msg);
    }
}
```

### N2 `Template/src/main/java/com/yin/utils/dataBase/SyncFailureLogger.java`

**作用**：把失败明细写到本地文件，**不依赖数据库**。数据库不可用时依然可以落盘。

**完整代码**：

```java
package com.yin.utils.dataBase;

import cn.hutool.json.JSONUtil;
import lombok.extern.slf4j.Slf4j;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.util.LinkedHashMap;
import java.util.Map;

/**
 * 数据同步失败明细的本地日志记录器。
 *
 * 落盘位置由 logback-spring.xml 中的 SYNC_ERROR logger 决定：
 *   logs/data-sync-error.log（按天滚动，保留 30 天）
 *
 * 不依赖任何数据库，数据库不可用时依然可以记录。
 */
@Slf4j
@Component
public class SyncFailureLogger {

    /** 独立 logger，路由到独立文件，不污染主日志 */
    private static final Logger FAIL_LOG = LoggerFactory.getLogger("SYNC_ERROR");

    /** 是否同时写 error_log 表（默认关闭，避免数据库不可用时二次失败） */
    @Value("${sync.failure.write-db-error-log:false}")
    private boolean writeDbErrorLog;

    public boolean isWriteDbErrorLog() {
        return writeDbErrorLog;
    }

    /**
     * 记录一条失败明细（行级）。
     *
     * @param record 失败明细，字段见 buildRecord
     */
    public void record(Map<String, Object> record) {
        try {
            FAIL_LOG.error(JSONUtil.toJsonStr(record));
        } catch (Exception e) {
            // 写本地日志本身失败不能影响主流程
            log.error("写入同步失败本地日志异常: {}", e.getMessage(), e);
        }
    }

    /**
     * 记录一条汇总信息（批次级）。
     */
    public void recordSummary(Map<String, Object> record) {
        try {
            FAIL_LOG.error("SUMMARY " + JSONUtil.toJsonStr(record));
        } catch (Exception e) {
            log.error("写入同步失败本地日志异常: {}", e.getMessage(), e);
        }
    }

    /**
     * 构造标准结构的失败记录。
     */
    public static Map<String, Object> buildRecord(String scheduledId, String detailId, String cronName,
                                                  String targetDs, String targetIp, String targetSchema,
                                                  String targetTable,
                                                  int chunkNo, int rowIndexInChunk, int globalRowNo,
                                                  Map<String, Object> rowValues,
                                                  String sql, Throwable error) {
        Map<String, Object> r = new LinkedHashMap<>();
        r.put("scheduledId", scheduledId);
        r.put("detailId", detailId);
        r.put("cronName", cronName);
        r.put("targetDs", targetDs);
        r.put("targetIp", targetIp);
        r.put("targetSchema", targetSchema);
        r.put("targetTable", targetTable);
        r.put("chunkNo", chunkNo);
        r.put("rowIndexInChunk", rowIndexInChunk);
        r.put("globalRowNo", globalRowNo);
        r.put("rowValues", rowValues);
        r.put("sql", sql);
        r.put("errorType", error == null ? null : error.getClass().getSimpleName());
        r.put("errorCode", extractErrorCode(error));
        r.put("sqlState", extractSqlState(error));
        r.put("errorMsg", error == null ? null : error.getMessage());
        r.put("rootMsg", error == null ? null : DataSourceCircuitBreaker.rootMessage(error));
        r.put("connectionError", error != null && DataSourceCircuitBreaker.isConnectionError(error));
        r.put("occurTime", java.time.LocalDateTime.now().toString());
        return r;
    }

    /**
     * 提取数据库原生错误码（不含方言前缀）。
     * Oracle: 1 -> ORA-00001（由调用方按 dsLx 拼前缀）
     * SQL Server: 2627 -> 违反唯一约束；8152 -> 字符串截断
     * MySQL: 1062 -> Duplicate entry
     */
    private static String extractErrorCode(Throwable error) {
        for (Throwable c = error; c != null; c = c.getCause()) {
            if (c instanceof java.sql.SQLException) {
                int code = ((java.sql.SQLException) c).getErrorCode();
                if (code != 0) {
                    return String.valueOf(code);
                }
            }
            if (c.getCause() == c) {
                break;
            }
        }
        return null;
    }

    /**
     * 提取 SQLState（跨库统一，23000 = 完整性约束冲突，22000 = 数据类型/长度问题）。
     */
    private static String extractSqlState(Throwable error) {
        for (Throwable c = error; c != null; c = c.getCause()) {
            if (c instanceof java.sql.SQLException) {
                String state = ((java.sql.SQLException) c).getSQLState();
                if (state != null) {
                    return state;
                }
            }
            if (c.getCause() == c) {
                break;
            }
        }
        return null;
    }
}
```

### N3 `Template/src/main/java/com/yin/config/DataSourceHealthChecker.java`

**作用**：定时检查各动态数据源的 Hikari 连接池状态，发现"空池 + 大量等待"僵死状态时重建池，实现自愈（对应"必须重启"的根因）。

**完整代码**：

```java
package com.yin.config;

import com.baomidou.dynamic.datasource.DynamicRoutingDataSource;
import com.yin.service.dataflowdb.impl.SysDatasourceServiceImpl;
import com.zaxxer.hikari.HikariDataSource;
import com.zaxxer.hikari.HikariPoolMXBean;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import javax.sql.DataSource;
import java.util.Map;

/**
 * 动态数据源连接池健康检查器。
 *
 * 判定僵死：连续 STUCK_THRESHOLD 次检测到"空闲连接为 0 且有线程在等待连接"，
 * 即认为该池已无法正常提供连接 -> 重建该数据源的连接池（removeDataSource + addDataSource）。
 */
@Slf4j
@Component
public class DataSourceHealthChecker {

    /** 连续几次判定僵死才重建，避免误判 */
    private static final int STUCK_THRESHOLD = 3;
    /** 检查间隔（毫秒），默认 30 秒 */
    private static final long CHECK_INTERVAL = 30_000L;

    @Autowired
    private DataSource dataSource;
    @Autowired
    private SysDatasourceServiceImpl sysDatasourceService;

    private final Map<String, Integer> stuckCounter = new java.util.concurrent.ConcurrentHashMap<>();

    @Scheduled(fixedDelay = CHECK_INTERVAL, initialDelay = CHECK_INTERVAL)
    public void check() {
        if (!(dataSource instanceof DynamicRoutingDataSource)) {
            return;
        }
        DynamicRoutingDataSource routing = (DynamicRoutingDataSource) dataSource;
        Map<String, DataSource> map = routing.getDataSources();
        if (map == null) {
            return;
        }
        for (Map.Entry<String, DataSource> e : map.entrySet()) {
            String dsKey = e.getKey();
            if (!(e.getValue() instanceof HikariDataSource)) {
                continue;
            }
            HikariDataSource hds = (HikariDataSource) e.getValue();
            HikariPoolMXBean mx;
            try {
                mx = hds.getHikariPoolMXBean();
            } catch (Exception ex) {
                continue;
            }
            if (mx == null) {
                continue;
            }
            int idle = mx.getIdleConnections();
            int awaiting = mx.getThreadsAwaitingConnection();
            if (idle == 0 && awaiting > 0) {
                int n = stuckCounter.merge(dsKey, 1, Integer::sum);
                log.warn("数据源 {} 连接池疑似僵死: 空闲连接={}, 等待线程={}, 连续次数={}",
                        dsKey, idle, awaiting, n);
                if (n >= STUCK_THRESHOLD) {
                    stuckCounter.put(dsKey, 0);
                    log.error("数据源 {} 连接池僵死，开始重建", dsKey);
                    try {
                        sysDatasourceService.rebuildDataSource(dsKey);
                        log.info("数据源 {} 连接池重建完成", dsKey);
                    } catch (Exception ex) {
                        log.error("数据源 {} 连接池重建失败: {}", dsKey, ex.getMessage(), ex);
                    }
                }
            } else {
                if (stuckCounter.containsKey(dsKey)) {
                    stuckCounter.remove(dsKey);
                    log.info("数据源 {} 连接池恢复正常", dsKey);
                }
            }
        }
    }
}
```

### N5 `Template/src/main/java/com/yin/utils/dataBase/DataSourceUrlBuilder.java`

**作用**：把 `sys_datasource.connection_params` 里的附加连接参数，按**库类型**用正确的分隔符拼到 URL 后面。

> 解决的问题（P20）：三种库的分隔符与单位都不同（Oracle/MySQL 用 `?` `&`，SQL Server 用 `;`），
> 手写 URL 极易出错。交给代码统一处理，运维只填 `connection_params` 字段即可。

**完整代码**：

```java
package com.yin.utils.dataBase;

import com.yin.pojo.dataflowdb.SysDatasource;
import org.springframework.util.StringUtils;

/**
 * 数据源 URL 拼装器。
 *
 * 职责：把 sys_datasource.connection_params 中的附加连接参数拼接到 url 后面。
 * 分隔符按库类型区分：
 *   - SQL Server : ";"   （jdbc:sqlserver://host:1433;database=db;encrypt=true;...）
 *   - Oracle/MySQL: "?" 起头，已带 "?" 时用 "&"
 */
public final class DataSourceUrlBuilder {

    private DataSourceUrlBuilder() {
    }

    /**
     * 拼装最终使用的 JDBC URL。
     *
     * @param ds 数据源配置
     * @return 最终 JDBC URL；url 为空时返回 null
     */
    public static String build(SysDatasource ds) {
        if (ds == null || !StringUtils.hasText(ds.getUrl())) {
            return ds == null ? null : ds.getUrl();
        }
        String url = ds.getUrl().trim();
        String params = ds.getConnectionParams();
        if (!StringUtils.hasText(params)) {
            return url;
        }
        // 去掉用户可能误填的前导 ? 或 ;
        String p = params.trim();
        while (p.startsWith("?") || p.startsWith(";")) {
            p = p.substring(1);
        }
        if (!StringUtils.hasText(p)) {
            return url;
        }
        return url + separator(ds.getDsLx(), url) + p;
    }

    /**
     * 计算追加参数时使用的分隔符。
     */
    private static String separator(String dsLx, String url) {
        if (isSqlServer(dsLx)) {
            // SQL Server 连接串恒用 ";" 分隔
            return ";";
        }
        // Oracle / MySQL：URL 已带 "?" 时用 "&"，否则用 "?"
        return url.contains("?") ? "&" : "?";
    }

    public static boolean isSqlServer(String dsLx) {
        return dsLx != null && "SQLSERVER".equalsIgnoreCase(dsLx.trim());
    }
}
```

#### M1-2　第 45-72 行：`executeWithRetry` —— 分类重试 + 指数退避 + `poll()`

**现状**：

```java
    private <T> T executeWithRetry(String dsName, Supplier<T> supplier) {
        int attempt = 0;
        Exception lastException = null;

        while (attempt < maxRetryAttempts) {
            attempt++;
            DynamicDataSourceContextHolder.push(dsName);
            try {
                return supplier.get();
            } catch (Exception e) {
                lastException = e;
                log.warn("执行失败，第 {} 次尝试，错误信息: {}", attempt, e.getMessage());

                    try {
                        // 重试延迟：避免立即重试，给数据库恢复时间
                        Thread.sleep(initialInterval);
                    } catch (InterruptedException ie) {
                        Thread.currentThread().interrupt();
                        throw new RuntimeException("重试被中断", ie);
                    }
                }
            } finally {
                DynamicDataSourceContextHolder.clear();     // ← P8
            }
        }
        log.error("执行失败，已达到最大重试次数: {}", maxRetryAttempts);
        throw new RuntimeException("执行失败，已达到最大重试次数: " + maxRetryAttempts, lastException);
```

**调整为**：

```java
    /**
     * 公共重试方法。
     *
     * 调整点：
     * 1. clear() -> poll()：只弹出栈顶，保留外层 @DS 上下文
     * 2. 只有"连接类"异常才重试；数据类异常（SQL 语法/约束冲突）立即抛出
     * 3. 退避改为指数：1s -> 2s -> 4s
     */
    private <T> T executeWithRetry(String dsName, Supplier<T> supplier) {
        int attempt = 0;
        Exception lastException = null;

        while (attempt < maxRetryAttempts) {
            attempt++;
            DynamicDataSourceContextHolder.push(dsName);
            try {
                return supplier.get();
            } catch (Exception e) {
                lastException = e;
                // P6：数据类异常重试没有意义，直接原样抛出
                if (!DataSourceCircuitBreaker.isConnectionError(e)) {
                    throw new RuntimeException(e);
                }
                log.warn("执行失败，第 {} 次尝试，错误信息: {}", attempt, e.getMessage());
                if (attempt >= maxRetryAttempts) {
                    break;
                }
                try {
                    // 指数退避：1s -> 2s -> 4s，给数据库恢复时间
                    Thread.sleep(initialInterval * (1L << (attempt - 1)));
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("重试被中断", ie);
                }
            } finally {
                // P8：必须用 poll() 弹出栈顶；clear() 会清空整个 ThreadLocal 栈，
                //     导致外层 @DS("master") 上下文丢失
                DynamicDataSourceContextHolder.poll();
            }
        }
        log.error("执行失败，已达到最大重试次数: {}", maxRetryAttempts);
        throw new RuntimeException("执行失败，已达到最大重试次数: " + maxRetryAttempts, lastException);
    }
```

#### M1-7　新增方法：数据源探活 `ping`

**位置**：`MethodService` 类末尾（第 181 行之后）新增。

```java
    /**
     * 数据源探活：借一次连接执行一条最简查询。
     *
     * ⚠️ 探活 SQL **必须按库类型区分**（已在 Oracle 11g / SQL Server 2022 / MySQL 8.0 上实测）：
     *   - ORACLE    : 必须 "SELECT 1 FROM DUAL"
     *                  裸 "SELECT 1" 在 Oracle 11g 上报 ORA-00923: 未找到要求的 FROM 关键字
     *   - SQLSERVER : 必须 "SELECT 1"
     *                  带 "FROM DUAL" 报 "'DUAL' 不是有效的表名"
     *   - MYSQL     : 两种都支持，统一用 "SELECT 1"
     *
     * 用于任务开始前的快速可用性判断，避免不可用时逐行撞连接超时。
     * 依赖各库 URL 的连接超时属性兜底（见 §5.1 / §6）。
     *
     * @param ds             数据源配置（含 ip，便于日志定位到具体机器）
     * @param timeoutSeconds 语句超时秒数
     * @return true 表示可用
     */
    public boolean ping(SysDatasource ds, int timeoutSeconds) {
        if (ds == null) {
            return false;
        }
        // 探活 SQL 按库类型分支，不能用"通用"写法
        String probeSql = "ORACLE".equalsIgnoreCase(ds.getDsLx())
                ? "SELECT 1 FROM DUAL"
                : "SELECT 1";
        DynamicDataSourceContextHolder.push(ds.getDsKey());
        try (java.sql.Connection conn = dataSource.getConnection();
             java.sql.PreparedStatement ps = conn.prepareStatement(probeSql)) {
            ps.setQueryTimeout(timeoutSeconds);
            try (java.sql.ResultSet rs = ps.executeQuery()) {
                return rs.next();
            }
        } catch (Exception e) {
            // 带上 ip，排查第三方库多实例时能直接定位到"哪台机器不通"
            log.warn("数据源探活失败: dsKey={}, ip={}, schema={}, 原因: {}",
                    ds.getDsKey(), ds.getIp(), ds.getSchemaName(), e.getMessage());
            return false;
        } finally {
            DynamicDataSourceContextHolder.poll();
        }
    }
```

**M2-3a 列日期策略枚举与判定**

```java
    /** 列的日期处理策略 */
    private enum DateStrategy {
        /** 不做日期处理，原样传值 */
        NONE,
        /** Oracle: to_date(?, 'yyyy-mm-dd hh24:mi:ss') + 字符串值 */
        ORACLE_DATE_TIME,
        /** Oracle: to_date(?, 'yyyy-mm-dd') + 字符串值 */
        ORACLE_DATE,
        /** 非 Oracle: ? + java.sql.Timestamp 值 */
        PARAM_TIMESTAMP
    }

    /**
     * 计算每一列的日期处理策略（按列统一，整批共用一条 SQL）。
     *
     * 规则：
     * - ORACLE    + dataTypeMapping="年月日时分秒" -> ORACLE_DATE_TIME
     * - ORACLE    + dataTypeMapping="年月日"     -> ORACLE_DATE
     * - ORACLE    + dataTypeMapping="无"         -> NONE
     * - ORACLE    + 未配置/其它值                -> 整列采样：任一行是日期则 ORACLE_DATE_TIME，否则 NONE
     * - SQLSERVER / MYSQL                       -> 整列采样：任一行是日期则 PARAM_TIMESTAMP，否则 NONE
     */
    private Map<String, DateStrategy> resolveDateStrategies(List<String> columns,
                                                             List<Map<String, Object>> targetData,
                                                             SysDatasource sysDatasource,
                                                             Map<String, String> stringStringMap) {
        boolean oracle = "ORACLE".equalsIgnoreCase(sysDatasource.getDsLx());
        Map<String, DateStrategy> strategies = new LinkedHashMap<>();
        for (String col : columns) {
            DateStrategy s;
            String mapping = stringStringMap.get(col);
            if (oracle) {
                if ("年月日时分秒".equals(mapping)) {
                    s = DateStrategy.ORACLE_DATE_TIME;
                } else if ("年月日".equals(mapping)) {
                    s = DateStrategy.ORACLE_DATE;
                } else if ("无".equals(mapping)) {
                    s = DateStrategy.NONE;
                } else {
                    s = DateStrategy.NONE;
                    for (Map<String, Object> row : targetData) {
                        if (SqlLoggerDynamic.isDateArg(row.get(col))) {
                            s = DateStrategy.ORACLE_DATE_TIME;
                            break;
                        }
                    }
                }
            } else {
                s = DateStrategy.NONE;
                for (Map<String, Object> row : targetData) {
                    if (SqlLoggerDynamic.isDateArg(row.get(col))) {
                        s = DateStrategy.PARAM_TIMESTAMP;
                        break;
                    }
                }
            }
            strategies.put(col, s);
        }
        return strategies;
    }
```

```java
    /**
     * 生成 INSERT 语句。列顺序由外部固定，避免每行各自遍历 HashMap 导致列序不一致。

    private String buildInsertSql(String targetTable, List<String> columns,
                                  Map<String, DateStrategy> strategies) {
        StringBuilder sqlColumns = new StringBuilder();
        StringBuilder placeholders = new StringBuilder();
        for (int i = 0; i < columns.size(); i++) {
            if (i > 0) {
                sqlColumns.append(", ");
                placeholders.append(", ");

            } else if (s == DateStrategy.ORACLE_DATE) {
                placeholders.append("to_date(?, 'yyyy-mm-dd')");
            } else {
                placeholders.append("?");
            }
        }
        return String.format("INSERT INTO %s (%s) VALUES (%s)",
```

```java
    private List<Object[]> buildRows(List<Map<String, Object>> targetData, List<String> columns,
                                     Map<String, DateStrategy> strategies) {
        List<Object[]> rows = new ArrayList<>(targetData.size());
        for (Map<String, Object> item : targetData) {
            Object[] vals = new Object[columns.size()];

                } else if (s == DateStrategy.PARAM_TIMESTAMP) {
                    v = toTimestamp(v);
                }
                vals[i] = v;
            }
            rows.add(vals);

    /**
     * 把日期字符串 / java.util.Date 统一转成 java.sql.Timestamp。
     *
     * 供 SQL Server / MySQL 目标使用：避免把日期字符串交给服务端做隐式转换
     * （SQL Server 的隐式转换受 dateformat / 语言设置影响，易报错或丢精度）。
     */
    private java.sql.Timestamp toTimestamp(Object v) {
        if (v == null) {
            return null;
        }
        if (v instanceof java.sql.Timestamp) {
            return (java.sql.Timestamp) v;
        }
        if (v instanceof java.util.Date) {
            return new java.sql.Timestamp(((java.util.Date) v).getTime());
        }
        String s = String.valueOf(v).trim();
        String[] patterns = {"yyyy-MM-dd HH:mm:ss.SSS", "yyyy-MM-dd HH:mm:ss", "yyyy-MM-dd"};
        for (String p : patterns) {
            try {
                java.text.SimpleDateFormat sdf = new java.text.SimpleDateFormat(p);
                sdf.setLenient(false);
                return new java.sql.Timestamp(sdf.parse(s).getTime());
            } catch (Exception ignore) {
                // 试下一个格式
            }
        }
        // 无法识别则原样返回，由数据库报错，失败行定位机制会记录到本地日志
        return v;
    }
```

#### M2-4　新增方法：`locateFailedRows` —— 精确定位失败行

> **驱动行为已验证**（`ojdbc8-21.1.0.0.jar` 字节码确认）：
> `OraclePreparedStatement.generateFailedBatchResults` 用 `long -3` 填充失败元素，
> 即 `BatchUpdateException.getUpdateCounts()` 中失败位置的值为 `Statement.EXECUTE_FAILED (-3)`。
> 数组长度 = 整个批次数（`System.arraycopy` 补齐）；驱动默认遇错即停，
> 因此 `getUpdateCounts().length < 批次数` 时表示后续行**未执行**。

```java
    /**
     * 精确定位批次内失败的行，并把失败明细写入本地日志。
     *
     * 规则（**不同驱动语义不同**，详见 §5.4）：
     * - counts 中值为 Statement.EXECUTE_FAILED(-3) 的位置 = 失败行
     *   （Oracle ojdbc8、MySQL connector-j 会填 -3）
     * - counts.length == 批次数  -> 该行失败，其余行已成功，不重试
     * - counts.length <  批次数  -> 驱动在失败处停止，其后的行未执行，可安全续跑
     *   （SQL Server mssql-jdbc 属于此类，且**不会**填 -3 标记）
     * - counts 为空或无 -3 标记   -> 退化为逐行定位（覆盖 SQL Server）
     */
    private void locateFailedRows(String targetDs, String targetTable, String sql,
                                  List<Object[]> chunk, int chunkStartRow, int chunkNo,
                                  ScheduledDetails scheduledDetails, java.sql.BatchUpdateException e) {
        int[] counts = e.getUpdateCounts();
        int failIdx = -1;
        for (int i = 0; i < counts.length; i++) {
            if (counts[i] == java.sql.Statement.EXECUTE_FAILED) {
                failIdx = i;
                break;
            }
        }

        // 情况 A：拿到了失败标记
        if (failIdx >= 0) {
            recordRowFailure(targetDs, targetTable, sql, chunk, failIdx, chunkStartRow, chunkNo,
                    scheduledDetails, e);
            // 驱动执行了整个批次（counts 覆盖全部行）-> 其余行已成功，不重试
            if (counts.length >= chunk.size()) {
                log.info("批次 {} 失败行定位完成: 行号={}, 其余 {} 行已成功，不再重试",
                        chunkNo, chunkStartRow + failIdx, chunk.size() - 1);
                return;
            }
            // 驱动在失败处停止 -> 其后的行未执行，继续写入（下一轮批次）
            int from = failIdx + 1;
            if (from < chunk.size()) {
                log.warn("批次 {} 失败行定位完成: 行号={}, 剩余 {} 行未执行，继续写入",
                        chunkNo, chunkStartRow + failIdx, chunk.size() - from);
                retryRemainder(targetDs, targetTable, sql, chunk, from, chunkStartRow, chunkNo,
                        scheduledDetails, 0);
            }
            return;
        }

        // 情况 B：没拿到失败标记（counts 为空 / 长度异常 / 无 -3）
        // SQL Server mssql-jdbc 属于此类：遇错即停且不填 -3
        // 保守处理：整块逐行定位，精确到行
        log.warn("批次 {} 无法从 getUpdateCounts() 定位失败行，退化为逐行定位", chunkNo);
        for (int i = 0; i < chunk.size(); i++) {
            try {
                methodService.batchUpdate(targetDs, sql,
                        new ArrayList<>(chunk.subList(i, i + 1)));
            } catch (Exception ex) {
                recordRowFailure(targetDs, targetTable, sql, chunk, i, chunkStartRow, chunkNo,
                        scheduledDetails, ex);
            }
        }
    }

    /**
     * 续跑失败行之后未执行的行（最多递归 5 层，防止无限递归）。
     */
    private void retryRemainder(String targetDs, String targetTable, String sql, List<Object[]> chunk,
                                int from, int chunkStartRow, int chunkNo,
                                ScheduledDetails scheduledDetails, int depth) {
        if (from >= chunk.size() || depth >= 5) {
            return;
        }
        List<Object[]> remain = new ArrayList<>(chunk.subList(from, chunk.size()));
        try {
            methodService.batchUpdate(targetDs, sql, remain);
            log.info("批次 {} 剩余 {} 行补写成功", chunkNo, remain.size());
        } catch (java.sql.BatchUpdateException e2) {
            locateFailedRows(targetDs, targetTable, sql, remain, chunkStartRow + from, chunkNo,
                    scheduledDetails, e2);
        } catch (Exception e2) {
            log.error("批次 {} 剩余行补写异常, 起始行号={}", chunkNo, chunkStartRow + from, e2);
        }
    }

    /**
     * 记录单行失败明细到本地日志。
     */
    private void recordRowFailure(String targetDs, String targetTable, String sql, List<Object[]> chunk,
                                  int idx, int chunkStartRow, int chunkNo,
                                  ScheduledDetails scheduledDetails, Throwable error) {
        Map<String, Object> rowValues = new LinkedHashMap<>();
        Object[] vals = chunk.get(idx);
        for (int i = 0; i < vals.length; i++) {
            rowValues.put("col_" + i, vals[i]);
        }
        // 从目标数据源配置中取 ip / schema，便于回溯
        String targetIp = null;
        String targetSchema = null;
        try {
            LambdaQueryWrapper<SysDatasource> w = new LambdaQueryWrapper<>();
            w.eq(SysDatasource::getDsKey, targetDs);
            SysDatasource ds = sysDatasourceService.getOne(w);
            if (ds != null) {
                targetIp = ds.getIp();
                targetSchema = ds.getSchemaName();
            }
        } catch (Exception ignore) {
            // 取不到配置不影响失败记录
        }
        Map<String, Object> record = SyncFailureLogger.buildRecord(
                scheduledDetails.getScheduledId(),
                scheduledDetails.getId(),
                scheduledDetails.getToMc(),
                targetDs,
                targetIp,
                targetSchema,
                targetTable,
                chunkNo,
                idx,
                chunkStartRow + idx,
                rowValues,
                sql,
                error);
        syncFailureLogger.record(record);
        log.error("目标表 {} 第 {} 行写入失败，已记录到 logs/data-sync-error.log: {}",
                targetTable, chunkStartRow + idx, error.getMessage());
    }
```

```java
     * 不同数据库的取字段 SQL
     *
     * @param dbType      数据库类型
     * @param tableName   表名（可带 schema 前缀）
     * @param dsSchema    数据源配置的 schema_name（表名自带 schema 时优先用表名上的）

    private String getTableColumnsQuery(DbType dbType, String tableName, String dsSchema) {
        String schemaFromTable = null;
        String pureTableName = tableName;

        // 判断表名是否包含模式名（schema）
        if (tableName != null && tableName.contains(".")) {
            String[] parts = tableName.split("\\.", 2);
            schemaFromTable = parts[0];
            pureTableName = parts[1];
        }
        // 表名自带 schema 优先，否则用数据源配置的 schema_name

                ? schemaFromTable.trim()
                : (dsSchema == null ? null : dsSchema.trim());

                return "SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH AS DATA_LENGTH " +
```

### 5.1 各库连接超时属性对照（★ 单位不一致，且已实测修正）

> ⚠️ **本节数值已按本地三个库实测校正**（Oracle 11g R2 / SQL Server 2022 / MySQL 8.0.43）。
> **实测结论与部分官方文档描述不一致**，以实测为准。

| 数据库 | TCP 建连超时 | socket 读超时 | 登录超时 | 单位 | URL 分隔符 |
|---|---|---|---|---|---|
| **Oracle** (ojdbc8 21.1) | `oracle.net.CONNECT_TIMEOUT=5000` | `oracle.jdbc.ReadTimeout=600000` | `oracle.jdbc.loginTimeout=30000` | **毫秒** | `?a=1&b=2` |

#### 🚨 实测记录（这是本节最重要的一部分）

**① SQL Server 的 `socketTimeout` 单位是毫秒，不是秒！**

| 配置值 | 阻塞 5 秒的语句实测耗时 | 结论 |
|---|---|---|
| `socketTimeout=600`（**当前配置**） | **1342 ms** 就报 `Read timed out` | 600 = **0.6 秒** ❌ |
| `socketTimeout=5000` | **5017 ms** 报 `Read timed out` | 5000 = 5 秒 ✅ |

> 🚨 **当前 `sys_datasource` 里 SQL Server 的 `socketTimeout=600` 实际只有 0.6 秒**，
> 会把 **所有超过 0.6 秒的查询全部掐断** —— 慢查询场景直接崩。
> **必须改成 `socketTimeout=600000`**（10 分钟）。

**② mssql-jdbc 8.2.1 不识别 `connectTimeout` 这个连接属性**

| 配置 | 实测失败耗时 | 结论 |
|---|---|---|
| 不带 `connectTimeout` | 29805 ms | 实际生效的是 `loginTimeout=30`（秒） |
| 带 `connectTimeout=3` | 29817 ms | **完全一样 → 该属性被忽略** |

> `DriverPropertyInfo` 返回的属性列表里也只有 `loginTimeout` / `socketTimeout`，没有 `connectTimeout`。
> → `connectTimeout=5` 可以从配置里**删掉**（留着无害，但别误以为它生效）。

**③ MySQL 的 `socketTimeout` 是毫秒**

`socketTimeout=5000` → 阻塞语句在 **5117 ms** 被中断 ✅（`CommunicationsException: Communications link failure`）

**④ Oracle 11g 不支持裸 `SELECT 1`**

| SQL | 结果 |
|---|---|
| `SELECT 1` | ❌ `ORA-00923: 未找到要求的 FROM 关键字` |
| `SELECT 1 FROM DUAL` | ✅ 正常 |

**⑤ 各库探活 SQL 必须方言分支**（详见 §M1-7）：

| 库 | 探活 SQL |
|---|---|
| ORACLE | `SELECT 1 FROM DUAL` |
| SQLSERVER | `SELECT 1`（带 `FROM DUAL` 报 `'DUAL' 不是有效的表名`） |
| MYSQL | `SELECT 1`（`FROM DUAL` 也支持） |

**建议值（统一到"建连 5 秒 / 读 10 分钟"）**：

| 数据库 | 建连超时 | 读超时 | 登录超时 |
|---|---|---|---|
| Oracle | `oracle.net.CONNECT_TIMEOUT=5000` | `oracle.jdbc.ReadTimeout=600000` | `oracle.jdbc.loginTimeout=30000` |
| SQL Server | *（驱动不支持，用 loginTimeout 兜底）* | `socketTimeout=600000` | `loginTimeout=30` |
| MySQL | `connectTimeout=5000` | `socketTimeout=600000` | `loginTimeout=30` |

> **SQL Server 的 `loginTimeout` 还有一个坑**：它同时被用作"登录握手超时"和"JVM 层整体连接超时"，
> 且在 TCP 握手失败时驱动会**按 1 秒间隔反复重试 Prelogin**（实测日志里连续 30 次），
> 直到 `loginTimeout` 到期。所以 SQL Server 的"连不上"最多要等 `loginTimeout` 秒（30s）才暴露 —— 这是驱动行为，无法通过连接参数调小。

### 5.2 各库连接超时参数示例

> ⚠️ **推荐把这些参数填进 `sys_datasource.connection_params` 字段**（新字段），
> 由 `DataSourceUrlBuilder`（§N5）按库类型自动拼分隔符 —— 不用手工判断 `?` 还是 `;`。
> 本节的"直接追加到 URL"是**应急方案**（§6 / D5），适合生产库暂时无法加列时先止血。

**填 `connection_params` 字段（推荐）**：

```sql
-- Oracle（毫秒，& 分隔）
UPDATE sys_datasource SET connection_params =
  'oracle.net.CONNECT_TIMEOUT=5000&oracle.jdbc.ReadTimeout=600000&oracle.jdbc.loginTimeout=30000'
WHERE ds_lx = 'ORACLE';

-- SQL Server（socketTimeout 单位是毫秒！connectTimeout 驱动不识别，可去掉）
UPDATE sys_datasource SET connection_params =
  'loginTimeout=30;socketTimeout=600000'
WHERE ds_lx = 'SQLSERVER';

-- MySQL（connect/socket 毫秒，login 秒，& 分隔）
UPDATE sys_datasource SET connection_params =
  'connectTimeout=5000&socketTimeout=600000&loginTimeout=30'
WHERE ds_lx = 'MYSQL';
```

**应急：直接追加到 URL（不依赖新字段与新代码）**：

```sql
-- Oracle 目标/源（? 与 & 分隔，单位毫秒）
-- jdbc:oracle:thin:@59.227.162.64:15210/SERVICE
UPDATE sys_datasource SET url = CONCAT(url,
  '?oracle.net.CONNECT_TIMEOUT=5000&oracle.jdbc.ReadTimeout=600000&oracle.jdbc.loginTimeout=30000')
WHERE ds_key = '<ORACLE 的 ds_key>';

-- SQL Server 目标/源（; 分隔，socketTimeout 单位是毫秒）
-- jdbc:sqlserver://10.0.0.9:1433;database=DB01;encrypt=true;trustServerCertificate=true
UPDATE sys_datasource SET url = CONCAT(url,
  ';loginTimeout=30;socketTimeout=600000')
WHERE ds_key = '<SQLSERVER 的 ds_key>';

-- MySQL 目标/源（? 与 & 分隔，connect/socket 毫秒、login 秒）
-- jdbc:mysql://10.0.0.8:3306/db?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai
UPDATE sys_datasource SET url = CONCAT(url,
  '&connectTimeout=5000&socketTimeout=600000&loginTimeout=30')
WHERE ds_key = '<MYSQL 的 ds_key>';
```

> ⚠️ **追加前必须先看现有 URL**：
> - Oracle / MySQL：若已带 `?`，用 `&` 追加；
> - SQL Server：若已带 `;`，用 `;` 追加；
> - MySQL 若要开启批量重写（见 §5.5），`rewriteBatchedStatements=true` 也一起加。

### 5.3 日期/时间戳值的跨库处理（★ 跨库写入的主要报错源）

**现状问题**（P16）：原代码只在 `dsLx=ORACLE` 时用 `to_date()`，其它库直接传原始 `String`。
当源库该字段是字符串型日期（如 Oracle 的 `VARCHAR2` 存 `'2026-11-03 12:00:00'`），
传到 SQL Server 的 `datetime` 列时会触发**服务端隐式转换**，受服务端 `dateformat` / 语言设置影响，
轻则精度丢失，重则直接报错。

**改造后的处理规则**（对应 M2-3a / M2-3b / M2-3c）：

| 目标库 | 占位符 | 传值方式 |
|---|---|---|
| Oracle | `to_date(?, 'yyyy-mm-dd hh24:mi:ss')` / `to_date(?, 'yyyy-mm-dd')` | 字符串（**沿用现有行为，零回归**） |
| SQL Server | `?` | `java.sql.Timestamp`（驱动转 `datetime2`） |
| MySQL | `?` | `java.sql.Timestamp`（驱动转 `datetime`） |

> **关键点：Oracle 分支的行为完全不变**，所以现有 Oracle 任务不会因为本次改造产生任何回归；
> SQL Server / MySQL 则改为传 `Timestamp`，消除隐式转换风险。

**SQL Server 目标表列类型建议**：优先用 `datetime2` 而非 `datetime`（`datetime` 只有 ~3.3ms 精度，
且范围 1753~9999）。若对方表已是 `datetime`，`Timestamp` 传值同样正常，只是精度受限。

### 5.4 批量失败时 `getUpdateCounts()` 的驱动差异（★ 定位算法的前提）

| 驱动 | 遇错行为 | `getUpdateCounts()` 长度 | 失败位标记 | 定位策略 |
|---|---|---|---|---|
| **Oracle** ojdbc8 | 遇错即停 | = 批次数（`generateFailedBatchResults` 用 `arraycopy` 补齐） | 失败位 = **-3**（`Statement.EXECUTE_FAILED`）✅ 已字节码验证 | 情况 A |
| **MySQL** connector-j 8.x | 默认**继续**执行剩余语句 | = 批次数 | 失败位 = **-3** | 情况 A |
| **SQL Server** mssql-jdbc | 遇错**立即停止** | **< 批次数** | **无 -3 标记** ⚠️ | **情况 B（逐行降级）** |

**结论：`locateFailedRows`（M2-4）的"情况 B：逐行降级定位"分支是 SQL Server 场景的必需路径，不可省略。**
若按 Oracle 的语义只实现"情况 A"，SQL Server 上将完全定位不到失败行。

**各库常见错误码（供 `logs/data-sync-error.log` 对照）**：

| 场景 | Oracle | SQL Server | MySQL |
|---|---|---|---|
| 唯一约束冲突 | `ORA-00001` | 2627 / 2601 | 1062 |
| 字段超长截断 | `ORA-12899` | 8152 | 1406 |
| 非空约束冲突 | `ORA-01400` | 515 | 1048 |
| 表不存在 | `ORA-00942` | 208 | 1146 |
| 数字转换失败 | `ORA-01722` | 245 | 1366 |

> `SyncFailureLogger` 记录的是**不带前缀的原生 errorCode + SQLState**（跨库统一），
> 前缀由 `ds_lx` 推断，见 M2-4 的 `recordRowFailure` 说明。

### 5.5 批量写入的性能特性差异

| 数据库 | `jdbcTemplate.batchUpdate` 的底层行为 | 额外优化 |
|---|---|---|
| Oracle | 逐条发送（可管道化），标准 JDBC batch | 无重写机制 |
| MySQL | 逐条发送 | **URL 加 `rewriteBatchedStatements=true`** → 驱动把 N 条 INSERT 重写为一条多值 INSERT，**性能提升最大** |
| SQL Server | 逐条发送 | mssql-jdbc 12.x+ 支持 `useBulkCopyForBatchInsert=true`（走 bulk copy），但对表有额外限制（外键/触发器/identity），且**失败行定位粒度会变粗** → **本次不建议开启** |

**因此本次方案：三种库统一采用"分块 + 标准 `batchUpdate`"**，SQL Server 不开 bulk copy，
MySQL 可选开 `rewriteBatchedStatements`（不影响失败行定位，因为重写后仍由驱动返回逐条 updateCounts）。

### 5.6 跨库场景下的其它注意点

1. **列名大小写**：
   - Oracle 会把未加引号的标识符**转成大写**；SQL Server 默认**不区分大小写**；MySQL 取决于平台。
   - 目标表名若在 Oracle 侧是 `T_BILL`，实际对象名是 `T_BILL`；而在 SQL Server 侧可能是 `t_bill`。
   - 改造后 SQL 仍由 `scheduledDetails.getToSql()` 决定，**建表/迁表时需确认目标库的实际对象名**。
2. **目标表可能带 schema**：`toSql` 里可能是 `dbo.TableName` / `YIN.MI_OPSPDISE_INFO_CS`（见 `SqlLoggerDynamic.java:110` 的示例），
   三种库都支持 `schema.table` 写法，**无需改造**。
3. **字段名含中文/特殊字符**：`SqlLoggerDynamic.fillSql`（第 18-65 行）解析 SQL 时用 `indexOf('(')` / `indexOf(')')`
   截取字段列表，**只支持第一个括号对**。目标表名本身带括号或字段名含 `)` 时会解析错误 → 影响失败日志的 SQL 填充，
   不影响实际写入（写入用的是 `?` 占位）。属遗留项，见 §9。
4. **字符集**：Oracle 源 → SQL Server 目标，中文乱码通常源于源端 `NLS_LANG` 或目标列的 collation。
   需确认源 Oracle 实例的字符集（如 `AL32UTF8`）与目标库一致。

### 5.7 数据源三个新字段的用法（ip / schema_name / connection_params）

#### 5.7.1 `connectionParams` —— 附加连接参数

**存放内容**：连接超时、读超时、登录超时等**附加 JDBC 参数**（不含 `jdbc:` 前缀和主机部分）。

**填写示例**（按各自库的单位，详见 §5.1）：

| 数据库 | `connection_params` 填写值 |
|---|---|
| Oracle | `oracle.net.CONNECT_TIMEOUT=5000&oracle.jdbc.ReadTimeout=600000&oracle.jdbc.loginTimeout=30000` |
| SQL Server | `loginTimeout=30;socketTimeout=600;connectTimeout=5` |
| MySQL | `connectTimeout=5000&socketTimeout=600000&loginTimeout=30` |

**生效路径**：
```
sys_datasource.connection_params
        ↓  DataSourceUrlBuilder.build(ds)   （按 ds_lx 选分隔符）
HikariConfig.setJdbcUrl(...)
        ↓
HikariCP 建连
```

**与 URL 中已有参数的关系**：
- `DataSourceUrlBuilder` 只负责**追加**，`url` 里原有的参数（如 `encrypt=true`、`useSSL=false`）**保持不变**；
- 若 `url` 已经带了同样的参数，**以 `connection_params` 为准**（会重复出现，驱动取最后一个 → 实际生效的是 `connection_params` 里的值）。
  → **建议：改造时把 URL 里已手工加的超时参数清掉，统一放进 `connection_params`，避免两处维护。**

**为什么值得单独放一个字段**：
| 好处 | 说明 |
|---|---|
| 免手工拼分隔符 | 三种库分隔符不同，代码统一处理，杜绝手误 |
| 免记单位 | 字段旁有注释说明该库用秒还是毫秒 |
| 可查询可审计 | `SELECT ds_key, connection_params FROM sys_datasource` 一眼看出每个库配了什么 |
| 改参数不用改 URL | 避免 URL 里参数越堆越长、难以排查 |

#### 5.7.2 `schemaName` —— 模式名

**各库对应关系**：

| 数据库 | `schema_name` 应填 | 用途 |
|---|---|---|
| Oracle | 目标表所属的 schema（如 `YIN`） | 查 `ALL_TAB_COLUMNS` 跨 schema 取字段；`INSERT INTO SCHEMA.TABLE` |
| SQL Server | 表所属的 schema（如 `dbo`） | `INFORMATION_SCHEMA.COLUMNS` 的 `TABLE_SCHEMA` 过滤；`INSERT INTO dbo.TABLE` |
| MySQL | 数据库名（如 `medical_insurance`） | `INFORMATION_SCHEMA.COLUMNS` 的 `TABLE_SCHEMA` 过滤；`INSERT INTO db.TABLE` |

**取值优先级**（已在 M8 / M10 中实现）：
1. 任务明细里配置的表名**已带** `.`（如 `dbo.TBill`）→ 用表名上的，忽略 `schema_name`；
2. 否则用数据源配置的 `schema_name`；
3. 都没有 → Oracle 用 `USER_TAB_COLUMNS`（当前用户），SQL Server/MySQL 不加 `TABLE_SCHEMA` 条件（保持原行为）。

**注意事项**：
- ⚠️ **Oracle 跨 schema 需授权**：查 `ALL_TAB_COLUMNS` 需要 `SELECT ANY TABLE` 或对该 schema 的对象授权。
  无权限时 `schema_name` **留空**即可（回退到 `USER_TAB_COLUMNS`）。
- ⚠️ **Oracle 的 schema 名默认大写**：`YIN` 与 `yin` 指向同一个 schema，M8 中已做 `toUpperCase()` 处理。
- ⚠️ **补全 schema 后的写入权限**：连接用户必须对该 schema 有 INSERT 权限。

#### 5.7.3 `ip` —— 数据库服务器 IP

**用途**（本次改造中实际用到的 3 处）：

| 位置 | 用法 |
|---|---|
| `MethodService.ping` 失败日志 | `log.warn("数据源 {} (ip={}) 探活失败: {}", dsKey, ip, msg)` —— 直接知道是哪台机器不通 |
| `DataSourceCircuitBreaker` 熔断日志 | 熔断时打出 ip，便于判断"是不是某台机器挂了" |
| `SyncFailureLogger` 失败明细 | 失败记录里带 `ip`，便于回溯 |

**建议**：由运维按实际连接地址填写；若一个 dsKey 对应多个实例（VIP），填 VIP 地址即可。

**字段不参与建连**：URL 中已含主机地址，`ip` 仅作**元信息与诊断**用。
⚠️ 因此 `ip` 填错**不会**导致连错库，但会让排查信息失真。

### D3 `sys_datasource` 表 —— URL 中的超时参数清理（可选但推荐）

若因故无法执行 DDL（生产库变更受限等），可**跳过 D1/D2**，直接按 §5.2 把超时参数写进 `url`。
此方案**不依赖任何代码改动**，可作为阶段 1 的应急上线手段。

| 对比 | D1+D2 方案（推荐） | D5 方案（应急） |
|---|---|---|
| 是否需要 DDL | 需要 | 不需要 |
| 是否需要代码 | 需要（N5 + M4-4） | 不需要 |
| 分隔符/单位 | 由代码统一处理 | 手工填写，易错 |
| 可维护性 | 好 | 差 |

> 两条路径**可以并存**：`DataSourceUrlBuilder` 只是"追加"参数，
> `url` 里已有的超时参数会保留（且 `connection_params` 里的会覆盖生效）。
> → 建议：先走 D5 应急止血，后续再补 D1/D2 规范化。

## 9. 本次不做的事 / 已知遗留

1. **不做幂等（MERGE）改造** —— 按约定"不用管对方库的插入情况，只是根据 cron 重试"。
   - **遗留风险**：cron 重跑会对上一轮已成功的行重复 INSERT。
   - 若目标表有唯一约束 → 重跑时这些行报 `ORA-00001`，会被记录到 `logs/data-sync-error.log`（不影响其它行）。
   - 若目标表无唯一约束 → 会产生重复数据。
   - **后续如需解决**：可按 §0 的 G6 方案 A-1（复用 `field_mapping.MAPPING_RULE = 'PK'` 标记主键，零 schema 变更）
     或 A-2（`scheduled_detatil` 增加 `to_key` 列）实现 MERGE。

2. **不做源查询分页 / 游标流式读取** —— 当前 `queryData` 使用 `queryForList` 一次性加载全量到内存。
   若源查询结果集很大，存在 OOM 风险。本次仅通过各库的读超时属性保证其不会永久挂死（见 §5.1）。

3. **不做任务级位点（checkpoint）** —— 同上，随 G6 一并处理。

4. **各库连接数上限未知** —— `maximumPoolSize=50` 是统一值，但三种库的服务端上限不同：
   | 库 | 服务端上限参数 | 超限时的报错 |
   |---|---|---|
   | Oracle | `processes` / `sessions` | `ORA-12520`（监听器无空闲进程）、`ORA-00933` |
   | SQL Server | `sp_configure 'user connections'` | 服务器拒绝连接 / `login failed` |
   | MySQL | `max_connections` | `Too many connections` (1040) |
   建议向各库管理员确认上限后，再按"并发慢查询数 + 任务并发数"调整 `maximumPoolSize`。

5. **`indexOfFailedElementsInBatch` 未使用** —— Oracle 驱动内部支持多失败元素追踪（`int[]`），
   当前实现按"遇错即停"处理，只定位第一处失败行。若需一次定位多个失败行，可改用该机制（需进一步验证驱动行为）。
   MySQL 驱动默认会继续执行剩余语句，理论上一次可拿到多个 -3，当前实现只取第一个（保守，不影响正确性）。

6. **日期字符串与 to_date 格式不匹配（改造前既有，未修复）** ——
   `SqlLoggerDynamic.formatDate`（`SqlLoggerDynamic.java:100-106`）对 `String` 入参是**原样返回**、不重新格式化。
   当 `dataTypeMapping="年月日时分秒"` 但源值是 `"2026-11-03"`（仅日期）时，
   Oracle 会执行 `to_date('2026-11-03','yyyy-mm-dd hh24:mi:ss')` 并报 `ORA-01861 格式不匹配`。
   修复方式：在 `toTimestamp`（M2-3c）旁增加一个"按目标格式重新解析并格式化字符串"的辅助方法，
   例如 `normalizeDateString(String v, String targetPattern)`，解析失败时原样返回以便暴露问题。

7. **`SqlLoggerDynamic.fillSql` 只解析第一个括号对** —— 该方法（第 18-65 行）用
   `indexOf('(')` / `indexOf(')')` 截取字段列表，目标表名含括号或字段名含 `)` 时会解析错误。
   **只影响失败日志里 SQL 的可读性，不影响实际写入**（写入使用 `?` 占位）。
   如需修复，改为用正则匹配最后一个 `(` 与最后一个 `)` 之间的内容。
